# 探测优先约束

## 规则

1. **不得假设目标发行版**：任何发行版专属结论前，必须先取得 `/etc/os-release` 的
   `ID`/`ID_LIKE`/`VERSION_ID`。未探测时，答案必须按族并列（Debian 系 / RPM 系 / Alpine）
   或明确限定适用范围。
2. **不得假设 init 系统**：先 `ps -o comm= -p 1`。非 systemd 时禁止输出 `.unit` 文件，
   改给 OpenRC / runit / s6 / supervisord / 入口脚本等价方案。
3. **不得假设包管理器**：`command -v apt-get dnf yum pacman apk zypper` 实测后再给安装命令。
4. **不得假设内核能力**：io_uring、cgroups v2、eBPF、命名空间特性须按 `uname -r` 与
   `/proc/config.gz` 或 `/boot/config-*`、`/sys/fs/cgroup` 挂载类型核对。
5. **不得假设资源上限**：fd 数、内存限额、CPU 配额、inotify 上限、ulimit 一律实测
   （`ulimit -a`、`/sys/fs/cgroup/...`、`/proc/sys/...`）。
6. **不得假设权限模型**：`id`、`getenforce`、`aa-status`、capability 集先查再给方案。
7. 探测脚本：`scripts/probe_os.py`、`probe_pkg.py`、`probe_toolchain.py`、`probe_systemd.py`、
   `probe_caps.py`、`probe_cgroup.py`、`probe_fs.py`。
8. 无法在目标机执行探测时，必须在结论首行标注「未探测，按 <假设> 给出」并列出待验证命令。

## 违反后果

- 包名/单元字段/路径不存在，用户执行即失败，且损害技能可信度；
- 把 systemd 方案塞进非 systemd 环境，导致服务无法拉起且难以定位；
- 忽略 cgroup 限额给出的并行度在容器里 OOM，属可预防事故。
